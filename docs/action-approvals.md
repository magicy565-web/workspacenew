## 核心契约

`ApprovalLedger(database, authorize, clock_ms=...)` 使用宿主指定的 SQLite 文件，新增 `hub_action_approvals` 和 `hub_action_approval_events`，不改写已有表。正式接入时必须由服务端选择当前空间的 `data_root() / 'studio.sqlite3'`；数据库路径不能来自浏览器、Agent 参数或来源文档。无第三方依赖。

`authorize(operation, action)` 是**必需的可信宿主回调**，必须实时读取认证身份和当前资源权限，返回 `Authority`。缺少回调、返回非 `Authority`、缺少对应 grant 或空间不一致，全部拒绝。操作名为 `request`、`read`、`decide`、`revoke`、`consume`。

`Authority.subject_id`、`kind`、`workspace_id`、`revision` 和 `grants` 不能由模型、页面表单或调用方的 JSON 自报后直接信任。`kind='human'` 必须来自真实人工登录通道；一个 Worker 的 owner token 不因此成为人工审批。

`revision` 是**拟执行动作的有效授权版本**，不是单纯的用户角色。接入层必须检查任务、执行批次、当前租约、Agent/工具权限、成员资格、资料授权和预算策略；发生取消、撤权、租约更换或策略变化时，应拒绝调用或改变这一版本。审批和消费都会重新检查它。接入层还必须处理业务撤权与消费之间的事务/执行端竞态；本模块自己的 SQLite 写锁不能锁住另一套账户数据库或远端工具。

## 不可变审批对象

`request(action, action_key, expires_at_ms)` 中的 action 必须恰好包含：

| 字段 | 含义 |
| --- | --- |
| `workspace_id` | 当前业务空间 |
| `task_id` | 实际任务 |
| `execution_id` | 实际执行批次 |
| `executor_id` | 唯一允许消费审批的 Worker 身份 |
| `action` | 具体工具动作名称，例如发信、报价或付款 |
| `parameters` | 完整工具参数，包括确切收件人、内容和必要的资源版本 |
| `budget` | 明确的 `currency` 与整数 `max_cost_minor`；零费用也显式填写 |

动作、幂等键、授权版本和绝对有效期共同生成 SHA-256 摘要。审批方必须提交实际展示对象的 `digest`；参数、接收方、内容、金额上限、币种、任务、执行批次、执行器、授权版本或有效期变化，不能继续复用旧审批。

参数只能是有限 JSON 值，整数限制在跨语言安全范围内；金额上限必须是非负整数，拒绝布尔值与浮点金额。JSON 深度最多 32 层，完整审批对象最多 64 KiB。这里的币种格式检查不等于外汇、币种精度或支付服务支持校验。

`max_cost_minor` 是审批绑定的预算上限，不是已经扣费的金额。本模块不会预留企业总预算、计费、换汇或控制支付供应商。正式工具适配器必须落实单次费用上限和总预算预留，不能把声明上限当成真实花费控制。

同一空间的 `action_key` 必须稳定代表同一次逻辑动作。原请求者重试完全相同的请求会取回原记录，包括拒绝、过期和已消费状态；改变对象或换请求者会冲突。不同空间独立。不得为了重试未知外部结果而自动换 key 或创建新审批。

## 状态与审计

正常路径：`pending → approved → consumed`。

拒绝：`pending → rejected`。撤销：`pending/approved → revoked`。到期：`pending/approved → expired`。终态不能重新批准或消费。

- `decide(id, digest, 'approve'|'reject', note='')` 仅接受带 `decide` 权限的人工身份。
- `revoke(id, digest, note)` 需要人工权限和非空原因。授权版本已经变化时，仍可由当前有权的人撤销旧审批。
- `consume(id, digest)` 仅允许绑定的 Worker，实时授权和版本检查通过后才能消费。
- `inspect(id)` 重新检查读取权限，返回不可变对象和审计事件的副本；观察到期时会持久化 `expired` 事件，因此并非绝对无写入的读取。

新审批有效期必须在当前服务端时间之后、24 小时以内；到期边界采用 `now >= expires_at`。授权回调返回后再次检查时间。已经观察并记录的过期不会因后续系统时钟回拨而复活；仍要求宿主提供可信的服务器时钟。

消费状态和审计事件使用同一个 `BEGIN IMMEDIATE` 事务。并发请求只能有一个获得新消费回执；审计写入失败会一起回滚。回执包含随机 `consumption_id` 和原审批对象，**它不是可反复使用的执行令牌**。

**批准不等于执行，消费不等于成功。** 进程在消费后退出时，记录保持 `consumed`；不能因为缺少结果便恢复审批。真正的外部调用、工具回执、未知结果及核对应继续使用已有的 `hub_execution` 体系。该账本只保证单条审批原子、至多一次消费，不宣称外部副作用 exactly-once。
