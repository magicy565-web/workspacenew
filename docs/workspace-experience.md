# Workspace experience and acceptance

This development build is a local workspace for coordinating external agents, with optional accounts and isolated shared workspaces. The caller supplies the model and execution tools. The interface must show the difference between a request that was saved, a task that was claimed, and a result that was actually returned. Teamily and QM informed the product direction; this build does not contain their private implementation or a running QM deployment.

## Primary journey

1. Open a quiet workspace with real recent conversations and one clear composer. Without history, the pane offers existing Agents; selecting one only chooses the next request's recipient. With history, restore the conversation with the latest real activity unless an explicit room URL, new-conversation state or newer user navigation takes precedence. Ordinary conversations default to automatic coordination. A saved workflow offers a sequence of steps; a persistent team opens its existing group conversation and current member set. These are separate choices.
2. Send a request. Save it immediately and show the assigned coordinator or explicitly selected agent when a task was actually created. In a team configured for named replies only, an unmentioned message is saved without a task. An unclaimed task says **等待 Agent 接手**. It must not say that a model is thinking or imply that connecting the webpage also connects an executor.
3. An external agent claims the task through MCP, CLI, or HTTP. Only a valid active lease permits the running state. The agent can return a validated task graph; dependencies appear in understandable order.
4. The agent returns a message and optional artifacts. The conversation shows the result and a small artifact entry; the detail area lets the user read, preview, choose a version, and download the exact saved file.
5. The user requests a change in the same conversation. The executor receives the conversation, shared context, and prior results. A new artifact revision preserves earlier versions. Switching versions never silently switches the download back to the latest version.

## Information hierarchy

- Main area: the user's request, agent replies, current task status, and artifacts relevant to the selected conversation.
- Navigation rail: labeled destinations for conversations, persistent teams, Agents and workflows. More opens skills, schedules, workspace search and the existing magazine application.
- Conversation pane: new conversation, real history with last speaker/time, local filtering and the actual Agent catalog for starting a request.
- Detail area: selected artifact or task detail. Keep scheduling events and integration instructions out of the primary reading flow.
- Connection entry: explain the external executor mode and provide usable setup commands. A zero-worker count is a connection fact, not an error or a reason to block writing a request.

## State language

| Stored state | Human-facing meaning |
| --- | --- |
| Team message saved without a target in mention mode | 消息已保存; do not invent a queued Agent task or answer |
| Queued, prerequisites complete | 等待 Agent 接手 |
| Queued, prerequisites incomplete | 等待前序任务 |
| Running with a valid lease | 正在执行; show the last reported progress if available |
| Lease expired | 等待重新接手; never retain a false active indicator |
| Completed | 已完成; available only after persisted completion |
| Failed | 执行失败; explain the reported error and offer retry |
| Failed with `recovery.decision = review_required` | 需要核对外部调用; keep the uncertain operation visible and require an explicit outcome decision before requeueing |
| Cancelled | 已取消; late executor output must not reappear as a success |

Parallel tasks should show independent progress. A failed dependency should make it clear why downstream work has not started. Retrying must preserve completed results. A connection issue must preserve the typed message and allow another attempt.

## Interaction quality

- The send button is disabled for empty input and while that submission is pending. Enter sends; Shift+Enter inserts a newline. Input method composition must not submit a partially composed Chinese word.
- Polling updates messages and task state without replacing the composer, selection, cursor, open editor, or chosen historical artifact revision.
- All actions have concise accessible names. Dialogs support Escape, keep focus inside while open, and return focus to the trigger when closed. Keyboard focus is visible.
- On narrow screens, navigation and artifact detail are separate dismissible surfaces. The composer and send action remain reachable, content wraps, and the viewport has no horizontal overflow.
- Persisted HTML is previewed inside a restrictive sandbox. Its content cannot execute scripts, access the parent app, submit forms, or silently contact remote services.
- Errors appear at the action that failed. Do not replace the entire interface with raw JSON or a generic alert for a recoverable failure.

| Adversarial scenario | Acceptance condition covered by the final integrated run |
| --- | --- |

| Another member resolves the currently selected call | Preserve the note while clearing the obsolete call and decision. Require explicit selection and a fresh decision for another call; never apply the previous call's draft to a different operation. |

## Persistent team acceptance

The v0.9 implementation adds a persistent team conversation, separate from a workflow template. In v0.8, `/templates` stored a fixed dependency graph and instantiated it for the first request. A later room message normally returned to the coordinator, the claim listed workspace agents rather than a team-bounded member set, and plans only checked that agents existed. Persistent room messages/sources were already present, but these behaviors did not establish a persistent team membership or its authorization boundary. The earlier 54 checks remain a v0.8 regression baseline, not acceptance of the new team model.

The agreed implementation contract uses a versioned team member set referenced by its room. Each run freezes its team version and member IDs; a coordinator's plan may use only the intersection of that frozen set and the team's current members. Adding a member cannot expand an already dispatched run. Removing a member atomically cancels every unfinished run whose frozen set contains that member, including its unfinished dependencies; completed results remain. Re-adding the member does not revive old runs or leases. The coordinator is an internal routing role, not an editable team member. Workspace owner/editor/viewer permissions remain separate from the AI member list.

The shortest complete journey is: create a team with a member set; open its persistent group conversation; add shared context/source material; send a request to an explicitly named member or the documented automatic coordinator; receive a real queued task and artifact; send a follow-up in that same room; verify the earlier material and current allowed members in the new claim; reload and return through the team directory to the same conversation. A workflow remains a separately labeled, editable sequence of steps. Team creation alone must not imply a connected executor or an executed model call.

| Required scenario | Evidence required before acceptance |
| --- | --- |
| Team, workflow and conversation remain distinct | Browser navigation separately exposes teams and workflows. Creating/editing team members does not change a DAG; editing a workflow does not silently change a room's team. Reopening a group preserves its room ID, messages, sources and artifacts. |
| Cross-message continuity | Two real dispatched requests in the same team room retain readable prior messages and source/artifact references. Source revocation affects subsequent claims, while existing historical references remain attributable. The claim identifies the team/version and its allowed members even when long context is omitted. |
| Explicit naming and automatic coordination | A member chosen through the UI receives the intended task; an unchosen nonmember cannot acquire membership through message text or request tampering. Automatic coordination is a queued coordinator task following the documented setting, not evidence that Teamily's private routing algorithm was recovered. |
| Plan membership and atomicity | A coordinator plan containing an outsider, a newly added member absent from the frozen set, or a removed member is rejected without partial tasks/artifacts. A valid plan uses the allowed intersection. A member task cannot recursively delegate. |
| Member edit conflict | Two editors start from the same team version; only one stale update can commit. The other gets 409, keeps its pending choices and must explicitly read the latest set before saving. Polling cannot silently alter checkbox choices or move focus. |
| Removal during queued or active work | After membership removal commits, affected unfinished runs are cancelled server-side. Their dependent tasks do not remain indefinitely queued. Completed artifacts and conversation history remain accessible, and the UI explains the membership-change cancellation. |
| Old executor and staged-result fencing | Old heartbeat, event append, result staging/read and completion are refused after removal. An already staged result cannot bypass cancellation through `submit_result`; no late message/artifact appears. Re-adding the member requires new work and never revives the former lease. |
| Authorization and workspace isolation | Viewers can read but cannot create/edit membership or dispatch work. Revoking a still-active executor credential immediately rejects writes. Team, room, run and member-update direct-ID routes enforce workspace scope; registering a worker for an Agent does not authorize that Agent for a team. |
| Concurrent return and member change | Tests order a late return after a successful membership update and verify rejection. A separately recorded true race may commit a result before the member change; it must retain an internally consistent history and cannot partially commit both interpretations. |
| Product interaction and mobile layout | At 390 pixels, the member picker, group composer, explicit-recipient control and conflict recovery remain reachable without horizontal overflow. Dialogs support Escape/focus return and keyboard-only choices. Polling/member updates retain drafts; a full reload retains persisted conversations and submitted requests. |
| Existing collaboration and recovery | The v0.8 comment→frozen request→artifact revision/candidate conflict journey still works; unknown tool outcomes stay review-required and old execution leases remain fenced. Team changes cannot erase an execution ledger or resolve comments automatically. |
